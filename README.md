# «Ничего не падает» — работа с расписанием

Консольное приложение на Kotlin: хранит корректные занятия, выбирает их по дате или типу и сообщает
об ошибках во входном файле. Главная идея — модель, которую нельзя испортить через публичный API:
все инварианты проверяются в конструкторе, а не только при чтении файла.

- [Условие задания](docs/assignment.md) · [Памятка](docs/student-guide.md)

## Сборка и запуск

Нужны **JDK 25** (в `JAVA_HOME` и в настройках Gradle в IntelliJ IDEA) и **Python 3.10+** для проверки.

## Этап 1. Модель

### Иерархия типов

```
sealed interface Session            date, topic
├── sealed class ActiveSession      + location, teachers   (общие проверки и защита списка)
│   ├── class Lecture               ≥ 1 преподавателя
│   ├── class Practice              ≥ 1 преподавателя
│   └── class Exam                  ≥ 2 разных преподавателей
└── class Cancellation              только date и topic
```

* `Session` — sealed: набор вариантов закрыт, `when (session)` проверяется компилятором на полноту без `else`,
  а «пятый тип» вне пакета создать нельзя.
* `ActiveSession` собирает общее для трёх действующих занятий: проверки и защита списка написаны один раз.
  Подклассы передают только минимальное число преподавателей — параметром конструктора, а не `abstract val`:
  конструктор базового класса выполняется до инициализации полей подкласса, и переопределённое свойство
  там было бы ещё равно 0.
* Все четыре класса конечные (в Kotlin классы `final` по умолчанию) — подкласс с ослабленными проверками не создать.
* У `Cancellation` **нет** свойств `location` и `teachers` — даже nullable. Обратиться к месту отмены нельзя
  уже при компиляции, а не «получить null во время выполнения».

### Почему `class`, а не `data class`

Выбран обычный `class` с написанными вручную `equals`, `hashCode`, `toString`.

1. **Защитная копия в `data class` невозможна.** Каждый параметр основного конструктора data class — это
   свойство, и `teachers` хранил бы ту самую ссылку, которую передали: `names.clear()` снаружи изменил бы объект.
   Нужен параметр конструктора, отличный от свойства, — это обычный класс.
2. **`copy()` — второй публичный конструктор.** `init`-проверки в нём выполнились бы, но
   `copy(teachers = mutableList)` сохранил бы чужой изменяемый список без копии (см. п. 1).
3. **`componentN()`** раскрывают внутреннее устройство и делают порядок полей частью API.

Цена — ручные `equals/hashCode/toString` (по разу в `ActiveSession` и `Cancellation`). Равенство учитывает
класс: лекция и практикум с одинаковыми полями — разные занятия.

Вместо `copy` есть только `internal fun withDate(newDate)` для переноса — он вызывает конструктор, поэтому
все проверки выполняются заново.

### Инварианты — проверяются в конструкторе, нарушение → `IllegalArgumentException`

| Правило | Где |
|---|---|
| год в `1..9999` (`LocalDate` сам допускает и 0, и 10000) | все типы |
| тема не пустая и не из одних пробельных символов | все типы |
| нет управляющих символов (`isISOControl`: `\t`, `\n`, `\u0000`, `\u007F`…) | тема, место, имена |
| нет пробельных символов в начале и в конце (включая неразрывный пробел); внутри — можно | тема, место, имена |
| место не пустое и не `-` | лекция, практикум, сдача |
| имя не пустое, не `-`, не `null` (на случай вызова из Java) | имена |
| нет повторов, регистр значим (`Ivanov` ≠ `ivanov`), порядок сохраняется | имена |
| ≥ 1 преподавателя / ≥ 2 у сдачи | лекция, практикум / сдача |

Ничего не исправляется автоматически: нет `trim`, смены регистра и удаления дубликатов — неверное значение
отклоняется. Сообщения понятные, например `Exam requires at least 2 different teacher(s), got 1`
или `Lecture: topic must not be empty or blank, got ""`.

### Защита коллекций

```kotlin
val snapshot = ArrayList(teachers)              // 1. своя копия — до проверок
requireValidTeachers(kind, snapshot, min)       // 2. проверяем ровно то, что сохраним
this.teachers = java.util.List.copyOf(snapshot) // 3. наружу — неизменяемый список JDK
```

* **Изменение исходного списка** (`names.clear()`) не влияет: объект хранит собственную копию. Копия делается
  *до* проверок, иначе можно было бы проверить один список, а сохранить уже изменённый.
* **Изменение через свойство** невозможно: `List.copyOf` возвращает неизменяемый список. Даже после
  `exam.teachers as MutableList<String>` вызовы `add`, `clear`, `set` и `iterator().remove()` бросают
  `UnsupportedOperationException`.
* Почему не просто `toList()`: в Kotlin/JVM он возвращает обычный `java.util.ArrayList`, который после
  приведения к `MutableList` спокойно меняется. Тип `List<String>` в Kotlin — интерфейс «только для чтения»,
  а не гарантия неизменяемости.

Тесты: `6 clearing the source list does not change the exam` и `7 list from the property cannot be modified even after a cast`.

## Реестр и журнал

`InMemorySessionRepository` хранит занятия в `ArrayList`: порядок сохраняется, одинаковые занятия лежат
отдельно. `all()` возвращает **снимок** — новую копию в неизменяемой обёртке: последующие `add` его не меняют,
а через него нельзя изменить реестр. `addAll(repository.all())` тоже безопасен.

`AuditedSessionRepository(delegate)` реализует интерфейс через `SessionRepository by delegate`:

* `all()` компилятор пробрасывает во внутренний реестр сам — событий не создаёт;
* `add` и `addAll` переопределены явно: сначала вызов делегата, потом **одно** событие (`ADD, 1` или
  `ADD_ALL, size`), в том числе `ADD_ALL, 0` для пустого списка;
* если делегат бросил исключение, события нет — журналируются только успешные операции;
* `addedCount` — общее количество добавленных занятий, `auditLog()` — снимок журнала.

После `add(одно)` и `addAll(три)`: `Sessions: 4`, `Added: 4`, `Audit events: 2`
(тест `one add and a batch of three give four sessions and two events`). Журнал в консоль не печатается.

### Почему переопределить только `add` недостаточно для учёта `addAll`

Делегирование — это не наследование. Для непереопределённого `addAll` компилятор генерирует в обёртке
`override fun addAll(sessions) = delegate.addAll(sessions)`. Дальше работает внутренний реестр, и даже если
его `addAll` внутри вызывает `add`, это `this.add` *делегата*, а не обёртки: обратного виртуального вызова
в обёртку нет. Пакетное добавление прошло бы мимо журнала целиком.

Обратная ошибка — реализовать `addAll` обёртки циклом по своему `add` — дала бы N событий `ADD` вместо одного
`ADD_ALL`. Поэтому обе операции переопределены явно, и каждая вызывает делегат ровно один раз. Тест
`delegate that implements addAll through add does not cause double logging` проверяет это на делегате,
у которого `addAll` реализован через `add`.

## Этап 2. Разбор файла и ошибки как данные

```kotlin
sealed interface ParseResult {
    data class Accepted(val lineNumber: Long, val session: Session)
    data class Rejected(val lineNumber: Long, val reason: RejectReason)
}
```

`RejectReason` — sealed-иерархия с данными из строки (поле, значение, количество), без готового текста и без
`Throwable`. Текст строит отдельная функция `describe(reason)`, `formatRejection` добавляет `line N: `.

Парсер не использует исключения для управления потоком: всё, что может нарушить контракт модели, он проверяет
сам в заданном порядке и только потом вызывает конструктор. Если конструктор всё же бросит исключение — это
ошибка программы, и она не маскируется под «отказ строки». Определения «управляющий символ» и «внешний пробел»
общие для модели и парсера (`TextRules`), поэтому правила не расходятся. `ParserNeverThrowsTest` прогоняет
50 000 случайных строк из опасных фрагментов — ни одна не приводит к исключению.

### Порядок проверок (одна ошибка на строку)

1. Нет `|` → неверный разделитель (сюда же попадает пустая строка).
2. Полей не 5. `split` в Kotlin сохраняет конечные пустые поля: `a|b|c|d|e|` — это 6 полей.
3. Первое пустое или полностью пробельное поле.
4. Дата: строго `YYYY-MM-DD` из ASCII-цифр, год `0001..9999`, день существует.
5. Тип: ровно `LECTURE`, `PRACTICE`, `EXAM`, `CANCELLED`.
6. У сдачи менее двух элементов списка, которые непустые, непробельные и не `-`.
7. Остальное. Каждая категория проверяется по всем полям сразу: тема → место → преподаватели
   (в списке — первый подходящий элемент):
   1. управляющие символы;
   2. внешние пробельные символы;
   3. поля отмены не равны `-`;
   4. место действующего занятия равно `-`;
   5. пустой элемент или `-` в списке преподавателей;
   6. повторное имя.

Решения в неоднозначных местах:

* В пунктах 7.1–7.2 список преподавателей разбирается по запятым и у отмены тоже, поэтому `Ivanov, Petrov`
  даёт ошибку пробела у элемента ` Petrov`.
* Пункты 7.1–7.2 идут раньше 7.3, поэтому у отмены с местом `Room 1 ` будет ошибка пробела.
* Отдельной проверки «минимум 1 преподаватель» для лекции и практикума в файле нет: пустое поле ловит пункт 3,
  а `-` — пункт 7.5 (`invalid teacher name "-" at position 1`).
* Не-ASCII символы (например, кириллица) модель не запрещает — в задании их нет среди нарушений;
  в сообщениях об ошибках они экранируются.

### Сообщения

Обязательные:

```
line N: invalid field separator
line N: got 6 fields, expected 5
line N: empty required field "date"
line N: invalid date "2026-13-45"
line N: unknown session type "SEMINAR"
line N: type "EXAM" requires at least 2 teachers, got 1
```

Собственные (пункт 7):

| Причина | Сообщение |
|---|---|
| управляющий символ | `line N: control character in field "topic": "Tab\u0009inside"` |
| внешний пробел | `line N: leading or trailing whitespace in field "teachers": " Petrov"` |
| поле отмены не `-` | `line N: type "CANCELLED" requires "-" in field "location", got "Room 1"` |
| `-` вместо места | `line N: type "PRACTICE" requires a location, got "-"` |
| пустое имя или `-` | `line N: invalid teacher name "" at position 2` |
| повтор | `line N: duplicate teacher "Ivanov"` |

Экранирование значений в сообщениях (`quoted()`): `\` → `\\`, `"` → `\"`, управляющие и не-ASCII символы →
`\uXXXX` на каждую UTF-16 единицу (эмодзи → `😀`). Сообщение всегда остаётся одной строкой из
печатных ASCII-символов. Сами значения модели не меняются.

## Команды

* `period` — занятия с `from ≤ date ≤ to`: `2026-10-05 | LECTURE | Classes and delegation | Room 312`.
* `type` — занятия одного типа с преподавателями через `, `: `… | Room 401 | Portnov, Stepanova`;
  у отмены место и преподаватели — `-`.
* `errors` — причины в порядке строк и `Rejected: K of M`.

Файл обрабатывается потоково: каждая строка разбирается и сразу печатается, если подходит под фильтр;
в памяти ничего не накапливается, поэтому `huge.txt` на 2 млн строк проходит за секунды. Итог печатается
после чтения всего файла. Файл всегда проверяется целиком: отклонённые строки влияют на код завершения
`period` и `type`, даже если не попадают в фильтр.

Реестр в командах намеренно не используется: для фильтра хранить все занятия не нужно, а накопление всего
большого файла ради одного прохода противоречит требованию к памяти. Реестр — отдельный компонент хранения
со своим контрактом и тестами.

Коды: `0` — отклонённых строк нет, `1` — есть, `2` — неверные аргументы или ошибка чтения. Ошибки чтения
обработчики не перехватывают — их обрабатывает готовая точка входа (`Cannot read file`).

## Задание со звёздочкой: перенос занятия

```kotlin
fun <T : Session> T.rescheduledTo(newDate: LocalDate): RescheduleResult<T>
```

* Возвращает `Moved(session)` — новое занятие **того же класса** с прежними темой, местом и преподавателями.
  Сохраняется и статический тип: `lecture.rescheduledTo(d)` имеет тип `RescheduleResult<Lecture>`.
* Исходное занятие не меняется (модель неизменяемая).
* Новое занятие создаётся через конструктор — инварианты проверяются заново.
* Типизированные отказы `Refused(reason)`: `SessionCancelled` для отмены, `DateOutOfRange` для года вне
  `1..9999`, `SameDate` — перенос на ту же дату переносом не считается.
